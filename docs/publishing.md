# 首页与发布规范

为更新 README、撰写 Release、发布安装包或补充平台附件时使用。公开文字面向下载和使用应用的人，详细工程记录交付给维护者。

## 内容归属

| 位置 | 内容 |
| --- | --- |
| `README.md` | 产品定位、下载入口、核心功能、快速上手、文档与反馈、许可 |
| `docs/getting-started.md` | 安装、接口、字幕、下载、平台差异、常见问题 |
| GitHub Release | 本次更新的用户可见变化、实际安装包、升级须知 |
| `docs/development.md` | 构建、测试、签名、本地配置与打包 |
| 维护者交付记录 | 审查发现、验证过程、测试统计、环境阻碍和未完成验证 |

首页和 Release 不放详细审查报告、代理工作过程、本机验证路径或测试流水账。安全修复可以作为用户可见变化简要说明；完整审查证据单独交付。

## README 模板

按以下顺序组织；下载入口放在第一屏，平台差异放进使用指南：

```markdown
# TVBox

<一句话说明产品用途。附上产品图标与下载、指南、反馈导航。>

## 下载
<按平台列出系统要求、实际下载入口与稳定版 / 预览版渠道。>

## 功能
<四至六条用户可以完成的事情。>

## 快速开始
<从首次添加接口到开始播放的三步。>

## 参与项目
<问题反馈入口、反馈所需信息、开发文档链接。>

## 致谢与许可
<上游项目、项目许可及第三方声明。>
```

- 以实际发布包描述功能；开发分支中尚未发布的功能进入后续 Release。
- 首页不堆构建号、哈希、协议字段名或底层实现。准确的版本、构建号和签名状态放在 Release。
- 下载入口使用真实存在的附件。`releases/latest/download/` 仅用于稳定版中确实存在且名称稳定的文件；预览包使用对应发布页的附件地址。
- 复用仓库现有图标。截图需要明确的平台与版本，隐藏账号、私人接口、本机个人信息；无合适截图时省略，不制作冒充真实应用的界面图。

## Release 模板

正文使用 [`.github/RELEASE_TEMPLATE.md`](../.github/RELEASE_TEMPLATE.md)。这是维护者手动填写的正文模板，GitHub 不会自动套用。

标题使用 `TVBox <版本>`；平台独立预览版补充平台、Preview 和构建号。正文用一至两句话概括重点，按“下载 → 新增 → 改进 → 修复 → 升级须知 → 校验与源码”排列。没有内容的章节直接删除，避免为了凑结构重复同一条变化。

- 每条写清用户得到的能力或被修复的场景；保留有意义的平台限定。
- 新增、改进、修复只记录相对前一个适用版本的变化，不把已有能力反复写成新增。
- 下载表逐一对应已上传附件，列出系统、架构、版本与构建号；平台可以独立演进，不能从当前源码版本推断历史安装包版本。
- IPA 是否签名、macOS 是否公证、预览版是否仍存在重要限制，按实际包填写。
- 稳定版页面后补预览平台包时，在该行明确标注预览状态，不改变既有平台附件的版本描述。
- 常规操作与长期兼容说明链接到使用指南；本次迁移、破坏性变化和重要已知问题放在“升级须知”。
- 校验文件、精确源码和完整变更放在末尾折叠区。附件与发布标签不同时，逐个说明源码对应关系，不能将自动生成的 Source code 压缩包宣称为所有附件的源码。

## 发布流程与完成标准

1. **确认范围**：读取远端默认分支、目标 Release、已有附件和待发布提交。文档更新只发布文档提交，保留无关代码和本机安装状态。
2. **核对事实**：确认每个平台的系统要求、架构、签名、预览状态、构建号和精确源码。更新内容逐条能在相应已发布源码或已有变更记录中找到依据。
3. **准备正文**：重用上述模板，删除空章节和占位符。添加或替换 IPA / DMG 后，同步检查 README 下载入口、Release 下载表及“尚未提供”类说明。
4. **检查成品**：检查 Markdown 渲染、相对路径、标题锚点、附件链接及私密信息；内部审查结果另行交付。文档变更不要求重新构建应用。
5. **发布与复核**：在用户授权范围内提交并同步，重新读取远端内容，确认正文一致且下载链接可用。仅更新描述时，附件 ID、大小、摘要、标签及稳定版 / 预览版状态保持不变。

完成时向维护者提供：首页和 Release 链接、文档提交、模板位置，以及实际未完成的检查。只在远端复核通过后报告已发布。
